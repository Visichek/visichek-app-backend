================================================================================
FRONTEND REPAIRS — Photo / Signature uploads on the host form
Date: 2026-05-20
Re: the "CHANGES — Photo / Signature uploads on the host form" changelog
================================================================================

CONTEXT
-------
The host form now stores a storage OBJECT KEY (not a URL) in
`picture_image_url` / `signature_image_url`. That decision is correct and is
kept. The disparities were all on the READ / preview-on-reload path. The
backend has been changed to resolve those object keys for you, so most of the
frontend's reload logic should be deleted, not patched.

================================================================================
WHAT THE BACKEND NOW DOES (no frontend work needed for these)
================================================================================
Host responses (`GET /v1/hosts`, `GET /v1/hosts/{id}`) now include TWO new
read-only, presigned fields alongside the stored keys:

    pictureImageUrl    -> the durable OBJECT KEY you saved (unchanged)
    signatureImageUrl  -> the durable OBJECT KEY you saved (unchanged)
    pictureUrl         -> NEW: presigned, directly-renderable URL (resolved on read)
    signatureUrl       -> NEW: presigned, directly-renderable URL (resolved on read)

(Backend fields are `picture_url` / `signature_url`; the camelCase conversion
middleware serves them as `pictureUrl` / `signatureUrl`.)

These mirror branding's `logoObjectKey` (stored) vs `logoUrl` (computed). They
are regenerated on every read, baked into the precompute cache, and — for S3 —
are auth-less presigned URLs that an <img src> can load directly. Legacy host
rows that still hold a full `http(s)://…` URL or a leading-slash path are
passed through untouched, so old rows keep rendering.

================================================================================
DISPARITY-BY-DISPARITY: WHAT TO CHANGE ON THE FRONTEND
================================================================================

1. RESOLUTION VIA /v1/documents/{objectKey} — REMOVE IT.
   Disparity: `resolveDocumentUrl('/v1/documents/${encodeURIComponent(objectKey)}')`
   was wrong on four counts (passes an object key where the route expects the
   Mongo document `_id`; the route returns a JSON envelope, not image bytes;
   it requires a Bearer token an <img> can't send; object keys contain slashes
   that `encodeURIComponent` turns into %2F and break the single path param).
   Fix: DELETE the documents-endpoint resolution for host images. On reload /
   edit mode, use the `pictureUrl` / `signatureUrl` fields the host response
   now returns. There is no client-side resolution step anymore.

2. PREVIEW SOURCE SELECTION — simplify to two sources.
   Fix: in image-upload-field.tsx, the preview <img src> should be:
     - just after upload: the fresh `downloadUrl` held in component state
       (still correct — keep this), OR
     - on reload / edit: the `pictureUrl` / `signatureUrl` from the host record.
   Drop the `resolveDocumentUrl(...)` branch and the legacy-URL detection
   branch entirely — the backend already handles legacy values and returns a
   ready-to-use URL in `*Url`. The component should treat `*Url` as opaque.

3. WHAT THE FIELD COMPONENT RECEIVES.
   Note: ImageUploadField is documented as "value is the stored OBJECT KEY".
   That stays true for the SAVE path (onChange still emits the object key into
   `pictureImageUrl` / `signatureImageUrl`). But for the DISPLAY path it now
   needs the resolved URL too. Fix: pass BOTH to the field — e.g. a `value`
   (object key, for change tracking / save) and a `previewUrl` prop fed from
   the host record's `pictureUrl` / `signatureUrl`. Don't try to derive a
   preview URL from the object key on the client.

4. PUBLIC UPLOAD AUTH — RETRACTED. The frontend's cookie approach is correct;
   NO change needed.
   Original (WRONG) claim: that the public upload required an
   `Authorization: Bearer` header and a cookie alone would 403.
   Verified in the backend: the public upload route
   (`POST /v1/public/tenants/{tenantId}/uploads`) uses
   `verify_optional_kiosk_token`, and the underlying `_extract_token`
   (security/auth.py:123) takes the Bearer header FIRST and FALLS BACK to the
   `ACCESS_TOKEN_COOKIE` httpOnly cookie. So with `withCredentials: true`, the
   authenticated tenant session cookie authenticates the call exactly as it
   does for the private upload. On Free / Starter plans (no anonymous surface)
   the cookie principal must be a `super_admin` / `dept_admin` / `receptionist`
   scoped to the same tenant — which is exactly who can reach the host form
   (create/update is gated to super_admin / dept_admin), so the requirement is
   already satisfied. Keep the photo on visibility="public"; do NOT flip it to
   private; do NOT try to set an Authorization header.

THINGS THE FRONTEND GOT RIGHT (no change)
================================================================================

  - PUBLIC for photo, PRIVATE for signature. Correct.
  - Public upload authenticated via the session cookie (`withCredentials: true`).
    Correct — the route accepts the cookie; no Bearer header required.
  - Letting the public upload use the backend default purpose `kiosk_form`
    (not forcing `appointment_photo`). Correct — backend default is kiosk_form.
  - Signature private upload with purpose="system". Correct — accepted value.
  - Using the fresh `downloadUrl` for the instant just-uploaded preview. Correct.

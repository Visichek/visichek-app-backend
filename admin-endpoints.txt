WHY THIS DOCUMENT EXISTS
------------------------
Two adjacent issues landed in the same change:

   1. ``GET /v1/sessions`` (and the role-specific
      ``GET /v1/admins/sessions`` / ``GET /v1/system-users/sessions``)
      was always returning ``data: []``. The Active-sessions table
      on the Account tab rendered an empty body. Root cause: the
      ``record_session`` helper existed but was never wired into any
      login flow. The ``sessions`` collection was empty for every
      tenant. There was also no path that updated ``last_active_at``
      after the row was created.

   2. The platform-admin invite flow was missing three things the
      product spec calls for: a welcome email, mandatory 2FA on every
      invited admin, and an HTML email carrying the 2FA code so a
      brand-new admin can actually finish their first login. The
      env-pinned primary admin must keep using ``OTP_DEV_CODE`` so
      on-call recovery never depends on email.

This file is the contract the frontend reads. ``CLAUDE.md`` is the
codebase rules; this one is the runtime surface.


SESSIONS — WHAT NOW WORKS
-------------------------
``GET /v1/sessions`` (unified, any token) returns a non-empty list as
soon as the user has logged in once after the fix. Each row carries
everything the Account tab table needs to render the row WITHOUT a
follow-up request:

   {
     "id": "<session ObjectId>",
     "userId": "<admin or system_user id>",
     "userType": "admin" | "system_user",
     "ipAddress": "102.89.xx.xx",
     "userAgent": "Mozilla/5.0 ...",
     "deviceType": "desktop" | "tablet" | "mobile" | "unknown",
     "device": "Chrome (Windows)",
     "location": null,
     "isCurrent": true,
     "accessTokenId": "<db id of the access token backing this session>",
     "dateCreated": 1747486800,
     "lastActiveAt": 1747490112
   }

Field-by-field source of truth:

   ``device``         — parsed from the User-Agent header at login
                        time by ``services/session_service.parse_device_label``.
                        Output is short and human-readable
                        (``"Chrome (Windows)"``, ``"Safari (iOS)"``).
   ``deviceType``     — coarse class for the icon column.
   ``ipAddress``      — picks the first IP from ``X-Forwarded-For``
                        when present, otherwise ``request.client.host``.
   ``location``       — left null today; reserved for the geo
                        enrichment job (the geofencing pipeline writes
                        ``user_locations`` per request — that data is
                        joined into sessions in a later sweep).
   ``isCurrent``      — true when the row's ``access_token_id`` matches
                        the token resolving the current request.
                        Computed in ``services/session_service.retrieve_sessions``.
   ``lastActiveAt``   — bumped by ``repositories/session_repo.touch_session_by_token``
                        whenever the access token is re-resolved off
                        the in-process token cache. The 30-second
                        token-cache TTL caps DB write rate to at most
                        one bump per session per 30s.

Field naming on the wire is camelCase because of
``CaseConversionMiddleware`` in ``main.py``. The keys above are what
the FE will see; the underlying schema is ``schemas.session_schema.SessionOut``.


SESSIONS — WHERE THE WRITE HAPPENS
-----------------------------------
``security/cookie_utils.build_auth_response`` is the single chokepoint
every login / OTP-verify / refresh path goes through to install
cookies and emit the JSON response. It now:

   1. Decodes the JWT it's about to ship to recover the access-token
      DB id (the same value AuthPrincipal stores as
      ``access_token_id``).
   2. Peels the wrapper for the super-admin login shape
      (``{"user": {...}, "tenant": {...}}``) so it can read
      ``id`` / ``role`` uniformly.
   3. Fires ``services/session_service.record_session`` as an
      ``asyncio.create_task`` AFTER the cookies are set, so a slow or
      failing session-write can never block the login response.

The recorder is wrapped in a try/except — failure is logged via the
``security.cookie_utils`` logger and the user still gets their tokens.
Sessions are intentionally lossy under pressure rather than blocking
the login critical path.

Heartbeat:
   ``repositories/tokens_repo.get_access_token`` now calls
   ``_touch_session_safe(result.accesstoken)`` on every cache MISS
   (i.e. roughly once per 30s per active session — the token cache
   TTL is the natural debounce). The update is fire-and-forget via
   ``asyncio.create_task`` so the auth hot path is not slowed.


SESSIONS — REVOKE & LIST-ALL CONTRACT
--------------------------------------
Unified endpoints (any authenticated role):

   GET    /v1/sessions
   DELETE /v1/sessions/{session_id}        → 400 if id format invalid,
                                              404 if no matching row
                                              for this user+user_type
   POST   /v1/sessions/revoke-all          → { "revokedCount": N }
                                              (counts every other row
                                              for the same user+user_type)

Role-specific aliases still work for backwards compat:

   GET    /v1/admins/sessions
   DELETE /v1/admins/sessions/{id}
   DELETE /v1/admins/sessions          (revoke-all for admins)

   GET    /v1/system-users/sessions
   DELETE /v1/system-users/sessions/{id}
   DELETE /v1/system-users/sessions    (revoke-all for system users)

These call the same service layer — the unified path is what the
shared Account tab UI should use.


ADMIN INVITE — MODULAR PER-FEATURE PERMISSIONS
-----------------------------------------------
Existing endpoint:

   POST /v1/admins/signup
     Auth: any application admin (the inviter)
     Body:
       {
         "fullName": "Ada Lovelace",
         "email": "ada@example.com",
         "password": "<initial temp password>",
         "accessPreset": "content_only" | "support_only"
                        | "content_support" | "billing_only"
                        | "all_controls"      (default if omitted)
       }
     Returns 201 with the new AdminOut.

What ``accessPreset`` controls:
   ``config/role_permissions.py`` defines five slices of
   ``ADMIN_PERMISSIONS`` exposed via the ``ADMIN_ACCESS_PRESETS``
   dict. Each preset is a SUBSET of the full platform-admin
   permission list, so you can never accidentally grant more than
   "all_controls" through a preset.

      content_only      → blog / pricing-content reads (incl. plan
                          reads to write marketing copy). No write
                          paths.
      support_only      → base account / dashboard reads + future
                          ``/v1/support-cases`` write paths.
      content_support   → union of content_only + support_only.
      billing_only      → full write set on /v1/plans, /v1/subscriptions,
                          /v1/discounts, /v1/usage. No tenants /
                          content / support.
      all_controls      → legacy "platform admin can do everything"
                          default. Used by the env primary admin.

The selected preset is persisted onto ``admins.access_preset`` and the
matching ``permissionList`` slice is written at the same time. The
route gate in ``security/account_status_check.check_admin_account_status_and_permissions``
reads the live ``permissionList`` so a content-only admin literally
cannot call tenant / subscription / discount routes — the sidebar
filter on the FE and the backend enforcement match by construction.

New endpoint to re-scope an existing admin (Phase A of modular
control):

   PATCH /v1/admins/{admin_id}/access-preset
     Auth: any application admin who can call admin management routes
     Body: { "accessPreset": "<one of the five presets>" }
     Returns 200 with the refreshed AdminOut.

     - Re-derives ``permissionList`` from
       ``ADMIN_ACCESS_PRESETS[preset]`` and atomically updates both
       ``access_preset`` and ``permissionList`` on the admin row.
     - 403 ``The primary platform admin must remain on the all_controls
       preset.`` if the target is the env-pinned primary admin and the
       requested preset is anything other than ``all_controls``.
     - 404 if the admin id doesn't exist.

The change takes effect on the target admin's NEXT request because
``check_admin_account_status_and_permissions`` reads the live row via
the gate cache; the gate cache TTL bounds propagation to <= 5 minutes
in the worst case (cache miss path always reads fresh).


ADMIN INVITE — MANDATORY 2FA + INVITE EMAIL
-------------------------------------------
``services/admin_service.add_admin`` now:

   1. Forces ``mfa_enabled=True`` on every freshly invited admin.
      This is belt-and-braces with the platform policy flag
      ``enforce_totp_for_admins`` — flipping the platform flag off
      in the future cannot silently weaken posture for invited
      admins.

   2. Sends an HTML welcome email via the ``admin_invite`` template
      mounted in ``core/email/mounted_templates.py``.

      Template context:
         invitee_name    — display name from the invite body
         platform_name   — ``EMAIL_SENDER_NAME`` env (defaults to
                          "VisiChek")
         inviter_name    — best-effort display name of the calling
                          admin; falls through to "An administrator"
                          if the inviter row was deleted or is the
                          env primary admin (which has no DB row).
         email           — sign-in email (what was just created)
         temp_password   — the password the inviter chose. The body
                          tells the invitee to change it from
                          ``Settings → Account`` after first login.
         access_label    — friendly label derived from access_preset
                          (e.g. ``"content editor"``).
         login_url       — built from ``APP_BASE_URL`` env when set;
                          omitted otherwise. The HTML template hides
                          the button when no URL is available.

      The send is fire-and-forget; the admin row is created either
      way so the inviter can resend the temp password from the admin
      console if the email never lands.


ADMIN LOGIN — 2FA OTP DELIVERED BY EMAIL
-----------------------------------------
Existing two-step admin login:

   1. POST /v1/admins/login    → { otpRequired: true, otpChallengeId }
                                  when 2FA is required (i.e. mfa_enabled
                                  on the admin OR enforce_totp_for_admins
                                  on the platform policy).
   2. POST /v1/admins/verify-otp
        Body: { "otpChallengeId": "...", "otpCode": "..." }
      → standard auth response with cookies + body.

What's new on step 1:
   ``services/otp_service.create_otp_challenge`` now mails the OTP
   code to invited admins using the ``admin_otp_code`` HTML template.

      Template context:
         recipient_name   — admin.full_name
         platform_name    — EMAIL_SENDER_NAME (default "VisiChek")
         code             — the 6-digit OTP
         ttl_minutes      — derived from OTP_TTL_SECONDS / 60
                            (defaults to 5)
         requesting_ip    — left blank today; reserved for the IP we
                            piped through from the login request.

Env-pinned primary admin bypass:
   The admin matching the SUPER_ADMIN_EMAIL env (or the sentinel id
   ``656f7ac12b9d4f6c9e2b9f7d``) KEEPS using ``OTP_DEV_CODE`` even in
   production, and the OTP email is NOT sent for that account.

   Why: this account exists so on-call can always recover the
   platform if SMTP, DNS, or the admin's own inbox is wedged. Mailing
   the code would re-introduce the dependency the static dev code
   exists to avoid.

   Implementation: ``services/otp_service._is_primary_env_admin``
   matches both the sentinel id and SUPER_ADMIN_EMAIL (case
   insensitive) against the calling admin's row. Used in two places:

      - ``create_otp_challenge`` selects ``settings.otp_dev_code``
        instead of a random ``generate_otp_code`` for this account.
      - ``_send_admin_otp_email`` returns immediately for this
        account so the email is never dispatched.

   The same protection extends to env=development behaviour: every
   admin gets ``OTP_DEV_CODE`` when ``ENV != production`` so the
   normal dev login flow is unchanged.


ADMIN INVITE — PRIMARY ADMIN PROTECTION
---------------------------------------
``services/admin_service.remove_admin`` now refuses to delete the env
primary admin under any circumstance (matched by id sentinel or
case-insensitive SUPER_ADMIN_EMAIL). The same guard fires on:

   DELETE /v1/admins/account
     → 403 "The primary platform admin cannot be deleted."

   PATCH  /v1/admins/{admin_id}/access-preset
     → 403 "The primary platform admin must remain on the all_controls
            preset." when the requested preset is anything other than
            ``all_controls``.

The env primary admin has no DB row by default (it's synthesised in
``repositories/admin_repo.get_admin``), so the delete check covers
both "row exists but is the primary" and "id matches sentinel".

FORGOT PASSWORD — SELF-SERVICE FLOW (unauthenticated)
------------------------------------------------------
Before this change there was NO unauthenticated password-reset path.
The codebase had only:

   - POST /v1/auth/change-password            (authenticated, needs current pw)
   - POST /v1/admins/system-users/{id}/reset-password
                                              (application admin → any user)
   - POST /v1/system-users/{id}/reset-password
                                              (super_admin → tenant user)
   - POST /v1/system-users/bulk/reset-password
                                              (bulk version of the above)

None of those help a user who is locked out of their own account.
This change adds the missing self-service flow used by both
application admins AND tenant system users.

Two new endpoints, both unauthenticated:

   POST /v1/auth/forgot-password
     Body: { "email": "ada@example.com" }
     Response: 202 + { "requested": true }

     - ALWAYS returns the same 202 envelope, whether or not the email
       matched a real account. This is the standard defence against
       account enumeration via response diff / timing.
     - Internally: looks up the email against ``admins`` AND against
       ``system_users``. Each match mints its own single-use reset
       row in the ``password_reset_tokens`` collection and sends its
       own HTML email via the new ``password_reset`` template.
     - One email can correspond to one admin AND zero-or-more system
       users (system_user emails are unique per tenant, not per
       platform). The recipient gets one email per matching account
       so they can choose the right tenant from the link URL.
     - The env-pinned primary admin (sentinel id
       ``656f7ac12b9d4f6c9e2b9f7d`` or SUPER_ADMIN_EMAIL) is
       EXCLUDED from this flow. Recovery for that account is via
       ``OTP_DEV_CODE`` + env credentials — mailing a reset link
       would reintroduce the SMTP / inbox dependency the static
       creds exist to avoid.

   POST /v1/auth/reset-password
     Body: { "token": "<from the email>", "newPassword": "NewStr0ng!" }
     Response: 200 + { "reset": true }

     - Verifies token by sha256-hashing it and looking up the row in
       ``password_reset_tokens``. Fails 400 on missing / used /
       expired (default 60 min TTL).
     - Enforces the SAME password policy + history rules as the
       authenticated change-password path
       (``services/password_change_service._enforce_new_password_policy``
       equivalents). 422 if the password fails strength or matches
       one of the last N hashes.
     - On success:
         * Updates ``admins.password`` (admin) or
           ``system_users.password_hash`` (system_user).
         * Records the new hash in ``password_history``.
         * Revokes EVERY active access / refresh token for the
           account so an attacker holding a stale session is kicked
           out — forces a fresh login.
         * Marks this reset token used and invalidates every OTHER
           outstanding reset token for the same account so a parallel
           link cannot be redeemed.
         * Drops the gate-cache snapshot via
           ``core.queue.gate_cache.invalidate_gate`` so the next
           request reads fresh account state.
         * Emits a ``<user_type>.password_reset_self_service`` audit
           event (tenant-scoped for system users) with the requesting
           IP in ``details``.
     - 403 if someone manages to mint a token for the env primary
       admin out-of-band — that account is never resettable through
       this flow.


FORGOT PASSWORD — EMAIL TEMPLATE
---------------------------------
``email_templates/password_reset.py`` mounts at key ``password_reset``
and is dispatched by
``services/forgot_password_service._send_reset_email``.

Template context the service passes in:
   recipient_name   — user.full_name (falls back to "there")
   platform_name    — EMAIL_SENDER_NAME (default "VisiChek")
   reset_url        — ``${APP_BASE_URL}/reset-password?token=<token>``
                      when APP_BASE_URL is set; empty string otherwise.
   token            — raw URL-safe token (32 bytes via secrets.token_urlsafe).
                      Shown only when reset_url is empty so the recipient
                      can paste it into the FE form manually.
   ttl_minutes      — derived from the service's
                      ``RESET_TOKEN_TTL_SECONDS`` (default 60).
   requesting_ip    — pulled from ``X-Forwarded-For`` (first hop) or
                      ``request.client.host``.
   tenant_label     — best-effort ``tenant_companies.company_name``
                      for system-user emails; empty for admin emails.

The HTML body is self-contained (inline styles only) so it renders the
same across Gmail / Outlook / Apple Mail / mobile. Tone matches the
admin_invite + admin_otp_code templates.


FORGOT PASSWORD — TOKEN STORAGE
--------------------------------
``repositories/password_reset_repo.py`` owns the
``password_reset_tokens`` MongoDB collection:

   {
     "_id": ObjectId,
     "token_hash": "sha256 hex of the plaintext token",
     "user_id": "<admin or system_user id>",
     "user_type": "admin" | "system_user",
     "tenant_id": "<tenant id, or null for admin>",
     "created_at": <unix seconds>,
     "expires_at": <unix seconds>,
     "used": false,
     "used_at": null,
     "requesting_ip": "102.89.xx.xx" | null
   }

The plaintext token is NEVER stored — only ``sha256(token)``. A leak
of the collection alone cannot be weaponised; the attacker would also
need the plaintext from the email (which we never persist) or to
brute-force the SHA-256 of a 32-byte URL-safe token (intractable).

Helpers:
   create_reset_token(...)                    — insert a pending row
   get_reset_token_by_hash(token_hash)        — lookup by sha256 hex
   mark_reset_token_used(token_id)            — idempotent consume
   invalidate_outstanding_reset_tokens(...)   — invalidate all OTHER
                                                pending tokens for a
                                                user after a successful
                                                reset.

No periodic cleanup is required for correctness — expired rows are
rejected by the service layer's ``expires_at`` check. A nightly
cleanup of ``used=true`` and expired rows can be added later if the
collection grows large in practice.


FORGOT PASSWORD — VERIFICATION
-------------------------------
1. Unknown email (no enumeration leak):
      a. POST /v1/auth/forgot-password { "email": "nobody@example.com" }
      b. Response MUST be 202 ``{ "requested": true }``.
      c. NO email is dispatched. NO row is added to
         ``password_reset_tokens``. The SMTP log is empty.

2. Admin reset:
      a. POST /v1/auth/forgot-password { "email": "bob@example.com" }
         (Bob exists from the invite verification above).
      b. SMTP log MUST show an outbound ``"Reset your VisiChek
         password"`` email to bob@example.com containing a Reset
         button with a URL of the form
         ``${APP_BASE_URL}/reset-password?token=<32-byte token>``.
         If APP_BASE_URL is unset the body shows the raw token.
      c. POST /v1/auth/reset-password
            { "token": "<the token>", "newPassword": "NewStr0ng!" }
         → 200 ``{ "reset": true }``.
      d. POST /v1/admins/login with the OLD password → 401.
         POST /v1/admins/login with the NEW password → 2FA flow.
      e. Re-submitting the same token → 400 "This reset link has
         already been used."

3. Token expiry:
      a. Mint a reset row, manually set its ``expires_at`` to the
         past via Mongo shell (or wait > 60 min).
      b. POST /v1/auth/reset-password with that token → 400 "This
         reset link has expired."

4. Password policy:
      a. Forgot-password for any account.
      b. POST /v1/auth/reset-password with newPassword="weak" → 422
         carrying the policy's error list.

5. System user cross-tenant:
      a. Create the same email as a super_admin in TWO tenants.
      b. POST /v1/auth/forgot-password with that email → SMTP log
         shows TWO emails, each carrying a different token. The
         tenant_label line in each body identifies which tenant the
         link applies to.

6. Primary admin protection:
      a. POST /v1/auth/forgot-password with SUPER_ADMIN_EMAIL.
      b. Response MUST be 202 (no enumeration), but NO email is
         dispatched and NO row is added. Recovery uses
         OTP_DEV_CODE + env credentials.


NOT DONE / NOT NEEDED
---------------------
- No frontend changes were made — the session response was already
  documented to carry ``device`` / ``deviceType`` / ``isCurrent`` in
  ``api/v1/session_management_route.py``; the FE never received data
  because the table was empty. With this fix the existing render code
  works as designed.

- No precompute invalidation changes — sessions are NOT precomputed
  (the list is per-user and changes on every login). The unified
  ``GET /v1/sessions`` reads MongoDB directly, which is correct: the
  hot path is the 200-or-so requests/hour an active user actually
  triggers, not a once-per-session render.

- No gate-cache invalidation on access-preset change — the gate cache
  has a 5-minute TTL by design (per CLAUDE.md "Gate Cache
  Invalidation"). If we need same-request propagation we can wire
  ``invalidate_gate(admin_id, "admin")`` into
  ``update_admin_access_preset``; left out of this change so it
  doesn't double the blast radius.

- No SMS / push fallback for the admin OTP. Email is the only channel
  on the application-admin side today. Tenant users will get the same
  email treatment in a follow-up sweep (they currently rely on the
  ``OTP_DEV_CODE`` shortcut).

- No "resend invite" endpoint. The inviter can simply re-issue a
  ``POST /v1/admins/signup`` with a fresh password if the email
  doesn't land — duplicate-email detection rejects double-creation.
  We can add a dedicated resend if the support volume warrants it.

- No rate-limiting layer on POST /v1/auth/forgot-password beyond the
  global per-anonymous-IP limit (20/min by default — see
  ``RateLimitingMiddleware`` in main.py). If we see abuse we can add
  a per-email cooldown in ``password_reset_tokens`` (e.g. refuse to
  mint a new row when an unused row exists with ``created_at`` in
  the last 60s). Left out for now since the global limit caps
  realistic abuse.

- No periodic cleanup of expired / used rows in
  ``password_reset_tokens``. Expired rows are rejected by the
  service-layer check on ``expires_at`` so correctness is unaffected
  — only storage grows. Add a cleanup job (similar to the discount
  expiry / usage cleanup APScheduler jobs in main.py) if the
  collection becomes large in practice.

- No SMS or push fallback for the reset link. Email is the only
  channel today, same as the admin invite + OTP flows.


LIST PAGINATION — skip / limit CONTRACT (FRONTEND)
---------------------------------------------------
Updated: 2026-05-17
Affects: api/v1/admin_route.py
         (``GET /v1/admins/`` and ``GET /v1/admins/search``)

WHY THIS CHANGED
   The two admin GETs used a legacy ``start`` / ``stop`` query pair.
   ``GET /v1/admins/`` had no defaults, so calling it without query
   params produced a 422 ``VALIDATION_FAILED`` with
   ``loc: ["query", "start"]`` and ``loc: ["query", "stop"]``. The FE
   had to know two non-standard keys before it could render the first
   page. Every other paginated GET in this codebase already uses
   ``skip`` / ``limit`` (see ``core/list_params.py`` and
   ``api/v1/notification_route.py``), so the admin list was the
   outlier.

   The fix renames the params and adds defaults. No service or
   repository signature changed — the route translates ``skip`` →
   ``start`` and ``skip + limit`` → ``stop`` when calling
   ``retrieve_admins`` / ``search_admins_by_query``.

THE CONTRACT
   ``GET /v1/admins/?skip=<int>&limit=<int>``
   ``GET /v1/admins/search?q=<term>&skip=<int>&limit=<int>``

   skip   — int, default ``0``. Number of records to skip from the
            start. For page-based UIs: ``skip = page * limit``.
   limit  — int, default ``25`` for the list endpoint and ``50`` for
            search. Hard cap: ``200``. Requests above 200 are rejected
            with ``VALIDATION_FAILED`` (``le=200``); the FE should
            never depend on huge pages — paginate.

   Both params are optional. Omitting both returns the first default
   page. Omitting just ``skip`` is the natural shape for "first page
   with a custom size".

FRONTEND CALLING PATTERNS
   1. First page, defaults:
         GET /v1/admins/

   2. First page, custom size:
         GET /v1/admins/?limit=50

   3. Next page (page-based, 25 per page):
         GET /v1/admins/?skip=25&limit=25
         GET /v1/admins/?skip=50&limit=25
         GET /v1/admins/?skip=75&limit=25

   4. Search, first 50 matches:
         GET /v1/admins/search?q=jane

   5. Search, next page:
         GET /v1/admins/search?q=jane&skip=50&limit=50

RESPONSE META (for "Next" button wiring)
   Both endpoints are decorated with ``include_meta=True``, so the
   envelope carries ``meta`` alongside ``data``:

      {
        "success": true,
        "message": "Admins fetched successfully",
        "data": [ ...admins... ],
        "meta": {
          "skip": 0,
          "limit": 25,
          "hasMore": true
        },
        "requestId": "..."
      }

   FE rule of thumb: render the "Next" button when ``meta.hasMore`` is
   true. Do NOT compute it from ``data.length === limit`` — that's
   off-by-one on the last page (a full-final-page would falsely show
   "Next").

ERROR SHAPES TO HANDLE
   - ``skip < 0``     → 422 ``VALIDATION_FAILED`` (FastAPI ``ge=0``).
   - ``limit < 1``    → 422 ``VALIDATION_FAILED`` (FastAPI ``ge=1``).
   - ``limit > 200``  → 422 ``VALIDATION_FAILED`` (FastAPI ``le=200``).
   - Non-integer     → 422 ``VALIDATION_FAILED`` (type coercion).
   The FE should clamp at the UI layer too so users never see a 422
   from the page-size selector.

MIGRATION FROM start / stop
   FastAPI does NOT reject unknown query keys, so a frontend still
   sending ``?start=0&stop=25`` will receive a 200 — but the legacy
   keys are ignored and the response is the default page (first 25
   for the list, first 50 for search). This means a stale FE will
   silently render the wrong page when the user clicks "Next". Update
   every admin call site to ``skip`` / ``limit`` at the same time as
   this deploy; the symptom of a missed migration is "Next" never
   advancing past page 1.

NOT IN SCOPE
   - The full table contract (``sort``, ``q``, ``facets``, range
     filters described in ``backend-docs/tables-spec.txt``) is NOT
     applied to the admin list yet. These are the only two GETs that
     moved off ``start`` / ``stop``; the rest of the admin surface
     either takes no pagination or already uses ``skip`` / ``limit``.
   - No precompute fanout for ``admins.list`` — application admins are
     a small, low-volume audience and the direct Mongo read is well
     within budget. Add ``@register_precompute("admins.list",
     scope=PrecomputeScope.GLOBAL)`` if dashboard rendering ever
     becomes hot.

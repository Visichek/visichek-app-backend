# Public Visitor Recognition & Profile Linkage

## TL;DR

1. `POST /v1/public/tenants/{tenant_id}/submit` no longer 500s for returning
   visitors.
2. Every public submit now creates (or updates) a `VisitorProfile` keyed on
   phone **or** email, so subsequent submits using *either* channel are tied
   back to the same profile and visit counter.
3. `POST /v1/public/tenants/{tenant_id}/visitor-status` — non-PII recognition
   endpoint. Returns whether the tenant has seen this visitor before, plus
   visit counters and a **`visitor_id`** the frontend uses on submit.
4. `POST /v1/public/tenants/{tenant_id}/submit-by-visitor-id` — new minimal
   submit endpoint for a recognised visitor. No email, phone, or bio_data.
   Just `visitor_id` + `purpose` (+ `tenant_specific_data` when the tenant's
   config requires it).
5. The original `POST /v1/public/tenants/{tenant_id}/submit` still exists
   and is the only path for new visitors and for flows that need an ID
   re-upload. **Do not delete it.**
6. All PII edits stay on the authenticated receptionist / super_admin side.

## The 500 that was reported

```
File "/app/repositories/visitor_repo.py", line 96, in update_visitor
    raise ValueError(f"Visitor {visitor_id} not found")
ValueError: Visitor 69e8aebf654851f33188f768 not found
```

### Root cause

`visitors._id` is stored in MongoDB as an `ObjectId` (auto-generated by
`insert_one`), but `VisitorOut.id` exposes that value as a hex string. When a
returning visitor submitted and the service called
`update_visitor(existing.id, …)` it passed the hex string back into
`find_one_and_update({"_id": "<hex>"}, …)`. MongoDB stores the key as an
ObjectId, not a string, so the query matched zero documents and
`update_visitor` raised `ValueError`, which propagated as a 500.

### Fix

`repositories/visitor_repo.py` now coerces a string `_id` back to `ObjectId`
before every lookup / update via an internal `_coerce_id_filter` helper. Both
`get_visitor` and `update_visitor` use it. This also fixes silent lookup
misses from `get_visitor` elsewhere in the codebase (badge_service,
checkin_service `confirm_checkin`, visitor_service) that were passing string
ids through the same path.

## Profile linkage on public submit

Before the fix: `POST /v1/public/tenants/{tenant_id}/submit` upserted a
`visitor` row but never touched `visitor_profiles`. Returning-visitor
history, visit counts, and the masked lookup
(`/public/register/{tenant_id}/lookup`) all relied on `visitor_profiles`, so
kiosk check-ins never populated it.

After: `_submit_verified_checkin_core` calls
`_upsert_visitor_profile_from_submit` immediately after the visitor is
resolved. It:

1. Looks for an existing profile by **phone** first, then by **email**.
2. Creates a new profile if neither matches.
3. Fills in any missing fields (phone / email / company / portrait /
   id_type) so a future submit using the *other* channel still resolves to
   the same profile.
4. Stamps `last_verification_date` + `verification_method` when the visitor
   arrived with an ID file.
5. Increments `total_visits` and `last_visit_date`.

Wrapped in `try/except` that only logs — profile upsert can never block the
check-in. The companion `submit-by-visitor-id` route calls the same helper
so visit counters stay in sync regardless of which submit path is used.

### Matching semantics

A visitor is resolved by phone **or** email independently. Someone who
submits today with `email=a@x.com, phone=+111` and tomorrow with
`email=a@x.com, phone=+222` re-resolves to the same profile on the email
match; the new phone is stored if that field was empty. A visitor who
submits with a *different* email *and* a different phone is treated as new.

## Endpoints: when to use which

| Endpoint | Purpose | Payload | Who should call |
| --- | --- | --- | --- |
| `POST /v1/public/tenants/{tenant_id}/visitor-status` | Non-PII recognition check | `{ phone?, email? }` | Called first, on blur of the phone/email field |
| `POST /v1/public/tenants/{tenant_id}/submit-by-visitor-id` | Minimal submit for a known returning visitor | `{ visitor_id, purpose, tenant_specific_data }` | Called on submit when `/visitor-status` returned `visitor_id != null` |
| `POST /v1/public/tenants/{tenant_id}/submit` | Full submit with email/phone (optionally ID upload for verification) | `{ email, phone, purpose, bio_data, tenant_specific_data, id_file? }` multipart | Called on submit for new visitors, or when `visitor_id` was null, or when the visitor needs to re-scan their ID |
| `POST /v1/public/register/{tenant_id}/lookup` | Masked lookup (existing) | `{ phone?, email? }` | Self-registration flow's "returning visitor?" shortcut — kept for backward compatibility |

## `POST /v1/public/tenants/{tenant_id}/visitor-status`

Public, unauthenticated. Returns **no PII** — only whether the tenant has
seen this visitor before, plus the counters the kiosk needs to drive the
"welcome back" UX, plus a `visitor_id` handle the frontend will re-submit
back to the server. Rate-limited by the anonymous bucket (20/min).

### Request

```json
{ "phone": "+15551234567" }
```
or
```json
{ "email": "jane@example.com" }
```

Either `phone` or `email` is required (both are accepted — phone wins).

### Response — match, visitor record exists

```json
{
  "success": true,
  "message": "Visitor recognition status retrieved",
  "data": {
    "found": true,
    "visitorId": "6524abcdef0123456789abcd",
    "totalVisits": 5,
    "lastVisitAgoDays": 12,
    "idVerifiedRecently": true
  }
}
```

### Response — match, but no visitor record

```json
{
  "data": {
    "found": true,
    "visitorId": null,
    "totalVisits": 5,
    "lastVisitAgoDays": 12,
    "idVerifiedRecently": true
  }
}
```

Happens when a profile exists from the older `/register/{tenant_id}`
self-registration flow but the visitor never submitted a kiosk check-in. The
frontend should fall back to the email/phone-based `/submit` route.

### Response — no match

```json
{ "data": { "found": false, "visitorId": null, "totalVisits": null, "lastVisitAgoDays": null, "idVerifiedRecently": false } }
```

`idVerifiedRecently` is `true` when the profile's `last_verification_date`
falls within the tenant's `id_reverification_days` window (default 30
days). Use it to gate the "skip ID re-scan" fast path.

### Privacy design

| Threat | What we do |
| --- | --- |
| Raw PII leak (name/email/phone/company) | None of these are ever returned. |
| Profile-id leak | `profile_id` is *not* returned. |
| "Hashed profile id" as a stable opaque handle | Rejected — a stable hash per profile re-introduces the enumeration it was supposed to prevent, and it is not needed (submit-by-visitor-id already uses the visitor_id for this). |
| `visitor_id` leak | Returned. It is just a MongoDB ObjectId; its only use is as input to `submit-by-visitor-id`, which is itself a public endpoint. Leaking it does not expose any PII beyond the `found=true` signal. |
| Existence-check enumeration | Inherent to any matcher. Rate-limited by the anonymous middleware bucket (20/min). For stronger resistance, gate on OTP-to-phone — not a hash. |
| Visit counter leak | Low risk; needed for the "welcome back, N visits" UX. |

## `POST /v1/public/tenants/{tenant_id}/submit-by-visitor-id`

Minimal submit for a visitor the backend already knows. No email, phone, or
bio_data re-sent — those stay on the stored visitor record.

### Request

```json
{
  "visitorId": "6524abcdef0123456789abcd",
  "purpose": {
    "purpose": "Meeting with Engineering",
    "purposeDetails": "Quarterly review",
    "expectedDurationMinutes": 60
  },
  "tenantSpecificData": {
    "host_name": "Jane Smith"
  }
}
```

### Tenant-specific data: when is it required?

`tenant_specific_data` must include every field the tenant's active
check-in config declares as `required: true, category: "tenant_specific"`.
BIO-category fields (name, email, phone, company) are satisfied by the
stored visitor record — the frontend does **not** re-send them.

If the config has *no* required tenant-specific fields, the frontend can
submit `tenantSpecificData: {}` (or omit it entirely — it defaults to an
empty object).

The frontend already fetches the config from
`GET /v1/public/tenants/{tenant_id}/active-checkin-config`; filter
`required_fields` where `required && category == "tenant_specific"` to know
which keys the user still has to enter.

### Response

Standard `CheckinOut` payload — the new check-in in `PENDING_APPROVAL`
state, awaiting receptionist approval.

### Error cases

| Status | Reason |
| --- | --- |
| 400 | Missing required tenant-specific fields, or invalid `tenant_id` / `visitor_id` |
| 404 | Tenant or visitor not found (visitor_id must belong to the tenant) |
| 409 | Visitor already has a pending check-in |

### Why a separate route instead of changing `/submit`?

- Keeps the public contract crisp: `/submit` is full-payload (for new
  visitors or re-verification), `/submit-by-visitor-id` is minimal (for
  known returning visitors). No "some fields are required sometimes".
- Keeps backend validation simple — the required-field logic in each route
  knows its exact scope.
- The existing `/submit` route is unchanged and continues to work for every
  case that does not have a visitor_id. No regression risk for existing
  clients.

## Returning-visitor fallback on `/submit` (already present)

`_submit_verified_checkin_core` still backfills missing bio fields from the
stored visitor record via `_collect_returning_visitor_fallback`. A client
that cannot or does not use `submit-by-visitor-id` can still submit a
minimal payload to the old `/submit` endpoint (email + phone + purpose) and
the backend will fill in name / company / id_type from the stored profile.
`submit-by-visitor-id` is the preferred path when the id is known — it
avoids re-sending email and phone and skips the upsert work.

## Data model

| Collection | Purpose | Keyed on (within tenant) |
| --- | --- | --- |
| `visitors` | Per check-in identity record (bio_data, verification state) — `visitor_id` here is what `/submit-by-visitor-id` consumes | upserted on email OR phone match |
| `visitor_profiles` | Long-lived profile used for visit history & recognition | upserted on email OR phone match |
| `checkins` | Each kiosk submission (pending / approved / rejected) | keyed on `tenant_id + visitor_id` |

Both `visitors` and `visitor_profiles` are written on every public submit
(either route). They are intentionally separate so the existing
visitor-profile analytics / retention flows continue to work unchanged.

## Frontend changes required

### 1. Stop treating submit 500s as a backend outage

The fix removes the 500 for returning visitors. If your client had a retry
/ circuit-breaker on 500 specifically for `/public/tenants/*/submit`, that
branch will now be quiescent.

### 2. Wire `/visitor-status` into the kiosk form

1. Visitor enters phone *or* email.
2. On blur (or ~400 ms debounce), call
   `POST /v1/public/tenants/{tenant_id}/visitor-status`.
3. Switch on the response:

   | Response | Rendering |
   | --- | --- |
   | `found === false` | Full new-visitor form (name, company, optional ID upload, purpose, tenant_specific_data). Submit to `/submit`. |
   | `found === true && visitorId` | "Welcome back! You've visited us {totalVisits} times (last {lastVisitAgoDays} days ago). Just tell us the purpose." Show only `purpose` + required tenant_specific_data fields. If `idVerifiedRecently === true`, skip the ID-upload step entirely. Submit to `/submit-by-visitor-id`. |
   | `found === true && visitorId === null` | "Welcome back!" banner, but render the full form and submit to `/submit` (email/phone fall-through). Visit counters from the profile still apply. |

4. Store `visitorId` in component state so the submit handler can pick the
   right route without another round trip.

### 3. Tenant-specific fields

Always read the tenant's active config from
`GET /v1/public/tenants/{tenant_id}/active-checkin-config` on mount.
For the `/submit-by-visitor-id` path, render only
`config.required_fields` where `category === "tenant_specific"`. Ignore
BIO-category required fields (the backend fills them from stored data).

### 4. PII edits — do NOT expose them publicly

There is no public endpoint that lets the visitor edit their stored
name / email / phone / company. If the visitor's details are wrong, the
receptionist corrects them from the authenticated side via the existing
endpoints in `api/v1/visitor_profile_route.py`:

- `GET /v1/visitor-profiles/{profile_id}` — read
- `PATCH /v1/visitor-profiles/{profile_id}` — update

Both require a `receptionist`, `super_admin`, or `dept_admin` token.

### 5. Drop any previously-planned usage of `/visitor-prefill`

An earlier iteration of this doc introduced
`POST /v1/public/tenants/{tenant_id}/visitor-prefill` that returned raw
(unmasked) PII. That endpoint was removed before shipping. Use
`/visitor-status` (for recognition) and `/submit-by-visitor-id` (for
submission) instead.

LIMITATIONS UPDATE — FIELD-LEVEL FREE-PLAN GATES
==================================================
Added: 2026-05-17
Affects: services/me_limitations_service.py,
         services/tenant_settings_writer.py

Adds three new feature keys to the Free plan limitations manifest
AND wires server-side field-level enforcement on the tenant settings
update writer so direct PATCH calls cannot bypass the UI gate.

These features gate sub-sections of a SHARED endpoint
(``PATCH /v1/tenants/{id}/settings`` and the unified
``PATCH /v1/tenant-settings``). The endpoint stays available — only
the gated fields are silently dropped on Free.


WHAT FRONTEND READS
-------------------
``GET /v1/me/limitations`` now returns these additional entries inside
``deniedFeatures`` for Free-plan tenants:

   "email_preferences"
   "visitor_policies"
   "geofencing"

No new entries are added to ``deniedEndpoints`` — the gate is
feature-key only because the endpoint is shared with other still-
allowed settings sections (organisation, retention, etc.).

The matching frontend gate is the dual check
``isFreePlan || deniedFeatures.includes(key)`` in
``src/app/(tenant)/app/settings/_sections/advanced-tab.tsx`` — see
the spec for the per-section UX (hide vs. shaking-padlock overlay).


SERVER-SIDE ENFORCEMENT (silent drop)
-------------------------------------
``services/tenant_settings_writer.py`` now strips the gated fields
from the inbound update payload BEFORE the ``TenantSettingsUpdate``
Pydantic model is constructed. Pydantic's partial-update semantics
then leave the stored value untouched.

Mapping (key → schema fields on ``schemas/tenant_settings_schema.py``):

   email_preferences   →  send_welcome_email
                          send_host_notification_on_arrival
                          send_visitor_badge_email

   visitor_policies    →  require_id_scan
                          require_host_approval
                          require_consent_before_check_in
                          allow_self_registration
                          auto_checkout_after_hours
                          visitor_badge_expiry
                          visitor_badge_expiry_hours
                          self_registration_fields

   geofencing          →  geofencing_enabled
                          geofencing_radius_meters
                          geofencing_reference_lat
                          geofencing_reference_lng

Behaviour:
   - PATCH on Free with one of these fields → 200 response, but a
     subsequent GET shows the field UNCHANGED (silent drop).
   - PATCH on a paid tier → field updates normally.
   - Plan downgrade (paid → Free) does NOT mutate any stored values
     — the saved settings persist and re-take effect on upgrade.
   - Plan resolution failure → fields are NOT stripped. Better to
     honour the update than to silently swallow it for a tenant
     whose plan lookup failed.


WHY SILENT DROP, NOT REJECT
---------------------------
Same rationale as the KYC kiosk override (item #2 in the earlier
free-plan spec):

   1. The frontend already hides / locks the controls on Free, so a
      legitimate UI client never sends these fields. The only callers
      hitting them are direct API users testing the surface — and a
      200 with stripped fields is a less hostile failure mode than a
      422 with a single field name.

   2. Preserves the user's preference across plan changes. A tenant
      who configured visitor_policies on a trial that lapsed to Free
      keeps those values stored and re-honoured the moment they
      upgrade — no re-entry needed.

   3. Symmetric with how the rest of the limitations system already
      degrades: deniedFeatures is advisory to the frontend, and the
      backend writers are the enforcement layer.


WHERE TO MAKE FUTURE CHANGES
-----------------------------
Adding a new tier-extras feature key:
   services/me_limitations_service.py
     → ``_EXTRA_FEATURE_KEYS_BY_TIER`` dict (per-tier tuple)

Adding the matching field-strip logic on a shared endpoint:
   services/tenant_settings_writer.py
     → ``_GATED_FIELDS_BY_FEATURE`` dict (key → tuple of schema field
       names). The ``_strip_plan_gated_fields`` helper runs before the
       Pydantic model is built; no additional plumbing required.

Adding the same gate on a DIFFERENT writer:
   Copy the ``_strip_plan_gated_fields`` pattern, pointing
   ``_GATED_FIELDS_BY_FEATURE`` at that writer's schema fields. Both
   writers can reference the same feature key safely — the manifest
   exposes one key, and each writer enforces its own field subset.


VERIFICATION
------------
1. Free-plan tenant: ``GET /v1/me/limitations`` →
   ``deniedFeatures`` MUST contain
   ``["email_preferences", "geofencing", "visitor_policies", ...]``
   (sorted alphabetically alongside any endpoint-derived keys).

2. Same tenant: ``PATCH /v1/tenants/{tid}/settings`` with body
   ``{ "require_id_scan": true, "send_welcome_email": true,
       "geofencing_enabled": true, "company_display_name": "Acme" }``
   → 200 OK. Then ``GET /v1/tenants/{tid}/settings`` →
   ``company_display_name`` reflects "Acme" but the three gated
   fields show their PRIOR stored values (unchanged).

3. Upgrade tenant to Starter. ``GET /v1/me/limitations`` →
   ``deniedFeatures`` no longer contains the three keys. ``PATCH``
   with the same body → all four fields update normally.

4. Downgrade back to Free. ``GET /v1/tenants/{tid}/settings`` →
   the Starter-era values still stored (no mutation on downgrade).
   Subsequent ``PATCH`` of gated fields silently dropped per (2).

NOT DONE / NOT NEEDED
---------------------
- No precompute invalidation changes — ``tenant.settings`` precompute
  is already invalidated by the writer's ``invalidates=`` list. The
  stripped-fields payload writes through the same path and refreshes
  the cache as before.

- No frontend-side preference storage — the "hide locked items"
  toggle in the sidebar dropdown is purely client-side (localStorage,
  4-hour TTL) per the spec. No backend involvement; no API surface
  added.

- ``_ENDPOINT_TO_FEATURE_KEY`` is NOT updated. The three new keys are
  intentionally tier-level extras (no endpoint pattern) because the
  endpoint itself is shared with non-gated fields. Adding a fake
  endpoint pattern would also have invalidated the wrong cache
  segments on writes.

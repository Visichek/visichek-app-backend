FRONTEND CHANGES — Presigned-only uploads (BREAKING)
Date: 2026-05-21
================================================================================

WHAT CHANGED (one sentence)
---------------------------
All file uploads (private AND public/kiosk) are now PRESIGNED and two-step: the
server no longer receives file bytes. You ask for an upload URL, PUT the file
straight to that URL, then confirm. Downloads/previews are unchanged (still a
presigned/served `download_url`), with a new endpoint to refresh an expired one.

WHY
---
Bytes go directly browser -> storage (S3) instead of through the API. It's the
standard, scalable pattern: the API server is out of the file-transfer path,
uploads scale with storage not with our app servers, and quota is enforced on
the real stored size.


================================================================================
1. ENDPOINTS REMOVED  (delete all calls to these — they now 404)
================================================================================
  POST /v1/documents                       (direct multipart upload)
  POST /v1/documents/upload-intents         (old intent shape)
  POST /v1/documents/complete               (old complete shape)
  POST /v1/uploads/private                  (multipart byte upload)
  POST /v1/public/tenants/{tenant_id}/uploads   (multipart byte upload)

================================================================================
2. ENDPOINTS ADDED / KEPT
================================================================================
  ADDED:
   POST /v1/uploads/intent                              (private, step 1)
   POST /v1/uploads/confirm                             (private, step 2)
   POST /v1/public/tenants/{tenant_id}/uploads/intent   (public kiosk, step 1)
   POST /v1/public/tenants/{tenant_id}/uploads/confirm  (public kiosk, step 2)
   GET  /v1/uploads/url?object_key=...                  (mint a fresh download URL)

  UNCHANGED:
   GET    /v1/documents/{document_id}    (metadata + fresh download_url)
   DELETE /v1/documents/{document_id}
   GET    /v1/storage/quota
   GET    /v1/public/tenants/{tenant_id}/branding etc. (still return download URLs)

  INTERNAL (do not call from FE — listed so you don't accidentally use them):
   PUT /v1/documents/upload-local/{object_key}   only the LOCAL/dev backend's
                                                  presigned target; in prod the
                                                  upload_url is a real S3 URL.


================================================================================
3. THE NEW UPLOAD FLOW (this is the whole change for the FE)
================================================================================
Replace every "POST a multipart file" with THREE steps:

STEP 1 — get an upload URL
  POST /v1/uploads/intent
  Authorization: Bearer <token>
  Content-Type: application/json        <-- JSON now, NOT multipart
  {
    "file_name": "passport.jpg",
    "mime_type": "image/jpeg",          <-- the file's real content type
    "size": 482133,                     <-- file.size in bytes (advisory)
    "purpose": "id_document",           <-- see PURPOSES below (default "system")
    "field_id": "fld_abc"               <-- optional; the tenant-form field id
  }

  201 ->
  {
    "object_key": "id-docs/<tenant>/<uuid>.jpg",
    "upload_url": "https://<bucket>.s3...&X-Amz-Signature=...",
    "method": "PUT",
    "headers": { "Content-Type": "image/jpeg" },
    "expires_in": 3600,
    "backend": "s3",
    "purpose": "id_document",
    "field_id": "fld_abc"
  }

STEP 2 — upload the bytes DIRECTLY to upload_url (NOT to our API)
  Use the returned method + headers verbatim. Send the raw file as the body.

    await fetch(resp.upload_url, {
      method: resp.method,              // "PUT"
      headers: resp.headers,            // { "Content-Type": "image/jpeg" }
      body: file,                       // the raw File/Blob — NOT FormData
    });

  IMPORTANT:
   * Do NOT add the Authorization header to this request (it goes to S3, the
     presigned URL carries its own auth). Sending Bearer here can break the
     S3 signature.
   * Do NOT wrap the body in FormData. Send the raw file/blob.
   * The Content-Type you PUT MUST equal headers["Content-Type"] from step 1,
     or S3 rejects the PUT (it's part of the signature).
   * A successful PUT returns 200 (S3) or 204 (local). No JSON body.

STEP 3 — confirm
  POST /v1/uploads/confirm
  Authorization: Bearer <token>
  { "object_key": "id-docs/<tenant>/<uuid>.jpg" }

  201 ->
  {
    "object_key": "id-docs/<tenant>/<uuid>.jpg",
    "download_url": "https://...signed-GET...",
    "file_name": "passport.jpg",
    "mime_type": "image/jpeg",
    "size": 482133,                     <-- AUTHORITATIVE size read from storage
    "backend": "s3",
    "purpose": "id_document",
    "tenant_id": "...",
    "field_id": "fld_abc",
    "expires_in_seconds": 86400
  }

  Use `object_key` as the value you store on the parent record / drop into
  tenant_form_data / bio_data. Use `download_url` to preview immediately.

Public/kiosk uploads are IDENTICAL, just different paths:
  POST /v1/public/tenants/{tenant_id}/uploads/intent
  POST /v1/public/tenants/{tenant_id}/uploads/confirm
(Anonymous when the tenant's plan allows public uploads; otherwise send a
super_admin / dept_admin / receptionist Bearer token — same gate as before.)


================================================================================
4. PURPOSES (the `purpose` field on intent)
================================================================================
  "system"            default; generic authenticated upload
  "kiosk_form"        public kiosk form file fields
  "visitor_photo"
  "id_document"
  "appointment_photo"
  "branding"
  "host_photo"        IMAGE ONLY (jpeg/png/webp/gif/bmp/heic/heif) -> 415 otherwise
  "host_signature"    IMAGE ONLY (same set)

host_photo / host_signature reject non-image types with HTTP 415 at BOTH intent
(declared type) and confirm (stored type). SVG is rejected (XSS).


================================================================================
5. DOWNLOADS / PREVIEW
================================================================================
No change to how you read files: list/detail responses still embed a
`download_url` (and logos/favicons/photos still come back as URLs). These are
presigned and expire (default 24h).

NEW — refresh an expired URL without re-fetching the whole parent object:
  GET /v1/uploads/url?object_key=<key>&expires_in=86400
  Authorization: Bearer <token>
  200 -> { "object_key": "...", "download_url": "...", "expires_in_seconds": 86400 }

  Access rule: you must own the object, be in its tenant, or be an app admin
  (else 403); 404 if the object_key is unknown.
  expires_in is optional (60s .. 7 days, default 24h).

Best practice: store the `object_key`, NOT the `download_url`. Mint a fresh URL
via the list/detail payload or GET /v1/uploads/url when you actually render.


================================================================================
6. ERROR CASES TO HANDLE
================================================================================
  intent:
    413  file too large (> plan max_file_size_mb, or > 50 MB hard cap)
    415  non-image for host_photo / host_signature
    429  storage quota / document-count cap reached
    403  (public) plan disallows anonymous upload and no valid staff token
  PUT to upload_url:
    403/400 from S3  usually a Content-Type mismatch or the URL expired
                     (expires_in seconds) — re-run intent to get a new URL
  confirm:
    409  no object found for object_key  -> the PUT didn't happen/failed; retry
                                            the PUT then confirm again
    413  stored object > 50 MB
    415  stored object is not an image (image-only purpose)
    429  quota exceeded on the REAL size (object is deleted server-side; re-do)
    403  confirming an intent you didn't create / wrong tenant

Note: quota is enforced for real at CONFIRM (on the true stored size), so a
confirm can 429 even if the intent passed. If confirm rejects, the stored
object is discarded automatically — just surface the error.


================================================================================
7. SUPPORT-CASE ATTACHMENTS
================================================================================
Already two-step (intent -> PUT -> register). The intent now returns a real
presigned PUT target (method "PUT", Content-Type header) — same client handling
as section 3 step 2. The register call (POST .../attachments) is unchanged.
Paths unchanged:
  POST /v1/support-cases/{case_id}/attachments/intent
  POST /v1/admin/support-cases/{case_id}/attachments/intent


================================================================================
8. OUT OF SCOPE (no change)
================================================================================
Blog/CMS media uploads (POST /v1/media/upload-image, /upload-video,
/upload-media and /blog-uploads/*) are a SEPARATE subsystem on Cloudflare R2
that serves public CDN URLs and streams large videos. They intentionally keep
their current multipart endpoints — presigned downloads don't apply to public
CDN content. No frontend change there.

================================================================================
BACKEND CHANGES — Visitor badge PDF generation moved to the frontend
Date: 2026-05-29
================================================================================

Scope:   Check-in / visit-session flow
Compat:  BREAKING for any frontend that consumed the badge PDF off
         the check-in response, the bulk-badges endpoint, or the
         per-session badge download endpoint.

================================================================================
WHY
================================================================================

The backend was generating the visitor badge PDF on every check-in
using reportlab, uploading the bytes to DocumentStorageManager, AND
base64-encoding the same bytes into the check-in response. The PDF was
a single-page A6/A7 layout (name, host/department, date, QR, optional
photo) — pure presentation, no audit/compliance role. The rendering
pulled the visitor photo bytes from storage inline on every confirm
call, ballooned the JSON response, and duplicated work the frontend
already has the context to do (branding config, photo URL, session
snapshots).

Decision: the backend's only badge responsibility is signing the QR
token (security boundary — token is HMAC'd with the server secret).
Everything visual is the frontend's job. The signed token + session
snapshots are all the FE needs to render and print.

================================================================================
WHAT CHANGED ON THE WIRE
================================================================================

1. POST /v1/visitors/sessions/{session_id}/confirm
   - Response no longer contains `badge_pdf_base64` / `badgePdfBase64`.
   - Response shape:
       {
         "session": VisitSessionOut,
         "badge_qr_token": "VIS_..."   // null on Free plan
       }
   - On Free / badge-gated tenants, `badge_qr_token` is null — the FE
     renders "approved, manual entry only" instead of a printable
     badge (same behaviour as before, just no fake empty PDF string).

2. POST /v1/appointments/{appointment_id}/check-in
   - Response no longer contains `badge_pdf_base64` / `badgePdfBase64`.
   - Response shape:
       {
         "appointment_id": "...",
         "visitor_profile": VisitorProfileOut,
         "session": VisitSessionOut,
         "badge_qr_token": "VIS_..."   // null when issue_badge=false
       }

3. GET /v1/visitors/sessions/{session_id}/badge   — REMOVED
   - This endpoint streamed badge PDF bytes from storage. There is no
     stored PDF anymore. Re-print is now a pure FE concern: read the
     session, render the badge from its snapshots + `badgeQrToken`.

4. POST /v1/visitors/sessions/bulk/badges          — REMOVED
   - There is no per-id download path anymore. For "print all
     checked-in visitors", the FE iterates the active-sessions list
     and renders each badge locally.

5. POST /v1/visitors/sessions/bulk/confirm
   - Per-id result no longer carries `badgePdfObjectKey`. New shape:
       { id: "<session_id>", badgeQrToken: "VIS_..." }   // token optional
   - Same rendering rule: FE composes each printable badge locally
     from the per-session GET + the returned token.

6. VisitSessionOut / VisitSessionBase / VisitSessionUpdate
   - `badge_pdf_object_key` / `badgePdfObjectKey` field REMOVED. Every
     list/detail endpoint that returned visit sessions no longer
     includes this key. Frontends that referenced it must stop reading
     it (will be undefined; safe to drop).
   - Retained badge fields: `badge_qr_token`, `badge_format`,
     `badge_generation_time`, `badge_expiry`.

================================================================================
WHAT CHANGED IN THE CODE
================================================================================

services/visit_session_service.py
  - Dropped `from services.badge_service import generate_badge_pdf`.
  - Dropped `from datetime import datetime, timezone` (only used by
    the removed PDF rendering).
  - `confirm_check_in(...)`: no more visitor-photo download, no more
    `generate_badge_pdf` call, no more `DocumentStorageManager` upload,
    no more base64 encoding. Now: sign token → stamp badge metadata on
    the session → return `{session, badge_qr_token}`. The plan gate
    (`is_feature_enabled("/v1/badges", "POST")`) still applies; on
    Free, `badge_token` stays None and no badge metadata is written.
  - `check_in_from_appointment(...)`: dropped `badge_pdf_base64` from
    the return dict.
  - `download_badge_pdf(session_id, tenant_id)` — REMOVED. This was
    the helper behind GET /sessions/{id}/badge; it no longer has a
    backing artifact.

services/badge_service.py
  - `generate_badge_pdf(...)` — REMOVED. reportlab / qrcode / Pillow
    are no longer imported by this module on the badge path. The
    `validate_badge(qr_code_value)` helper is unchanged.
  - reportlab is no longer used anywhere in the request path. It can
    stay in requirements.txt for now (cheap on disk, easier rollback)
    or be dropped in a follow-up if nothing else picks it up.

schemas/visit_session_schema.py
  - Removed `badge_pdf_object_key: Optional[str] = None` from
    `VisitSessionBase` and `VisitSessionUpdate`. Existing Mongo
    documents that still carry this field are tolerated by Pydantic
    (extra-ignore) but the field is no longer surfaced.

services/checkin_service.py
  - `_send_visitor_badge_email(...)`: `badge_url` is now always `""`.
    The `try_resolve_download_url(badge.badge_pdf_object_key)` call
    was effectively dead code (Badge schema never had that field) —
    replaced with a constant empty string. The host-approval email
    template already hides the download button when `badge_url` is
    empty and leans on the QR / public badge page.

services/visitor_bulk_writer.py
  - Module docstring updated (4 bulk ops, not 5).
  - `_visitor_bulk_confirm`: per-id result is now
    `{id, badgeQrToken?}` instead of `{id, badgePdfObjectKey?}`.
  - `_visitor_bulk_badges` writer — REMOVED. No badge re-print queue
    operation exists anymore; the FE composes badges directly from
    the per-session GET.

api/v1/visitor_route.py
  - Dropped imports: `StreamingResponse`, `io`, `download_badge_pdf`.
  - Removed routes: `GET /sessions/{session_id}/badge`,
    `POST /sessions/bulk/badges`.
  - Stripped `badge_pdf_base64` from the confirm endpoint's
    `success_example`.
  - Stripped `badge_pdf_object_key` from every `success_example` in
    the file (8 occurrences across check-in / check-out / list /
    detail / draft-resume / host-approve / id-scan).
  - Updated docstring for `bulk_confirm` and `confirm_check_in_endpoint`
    to describe the new "sign token, FE renders PDF" contract.

api/v1/appointment_route.py
  - Stripped `badge_pdf_base64` from the `check-in` endpoint's
    `success_example`.

config/role_permissions.py
  - No changes required. The two removed routes were tenant-scoped
    and not enumerated as explicit permission keys.

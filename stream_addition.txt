================================================================================
STREAM ADDITION — real-time list updates over SSE (frontend + contract spec)
================================================================================
Engineering plan: plan-stream.md
Reference impls already live: GET /v1/notifications/stream, GET /v1/dashboard/live/stream

--------------------------------------------------------------------------------
WHAT THIS IS
--------------------------------------------------------------------------------
One Server-Sent-Events connection that tells your tables WHEN to refetch. It
does NOT push table data. When anything in your tenant (or, for app admins,
platform-wide) changes a list, the server publishes a tiny "this list changed"
ping; the FE refetches the normal list GET (already cache-fast). Pings are
idempotent hints — a missed one just means one missed refetch, so pair with a
refetch-on-window-focus safety net.

Why not push the data? The list GETs already exist and serve from precompute.
Pushing whole pages on every write is bursty (one write fans out to every
connected user of the tenant). Ping + refetch is lighter and reuses the
existing list contract verbatim.

--------------------------------------------------------------------------------
THE ENDPOINT
--------------------------------------------------------------------------------
GET /v1/stream
  Auth:    any logged-in user (same bearer/cookie auth as the rest of the API).
  Returns: text/event-stream, held open. Browser EventSource auto-reconnects.
  One connection per browser TAB is enough — it is multiplexed. Do NOT open one
  per table. The single connection carries pings for every list the user can
  see; filter client-side by `resource`.

On connect the server subscribes you to:
  - your tenant's channel  (if you belong to a tenant), and
  - the global channel     (only if you are an application admin).

--------------------------------------------------------------------------------
EVENT FORMAT
--------------------------------------------------------------------------------
event: list.invalidate
id: <monotonic seq, sent back as Last-Event-ID on reconnect>
data: {"resource":"appointments.list","op":"update","id":"<objectId>","ts":1716412345}

  resource : which list changed. Match against the precompute resource name
             (e.g. "appointments.list", "incidents.list", "hosts.list").
  op       : "create" | "update" | "delete" | "bulk".
  id       : the affected record id (best-effort; absent/empty for bulk).
  ts       : unix seconds.

Also sent:
  - `: keep-alive`  comment every ~20s (ignore; keeps proxies from dropping it).
  - `: connected`   comment once on connect.

The stream CLOSES when your auth token expires — the FE should refresh its
token and let EventSource reconnect.

--------------------------------------------------------------------------------
FRONTEND RECIPE
--------------------------------------------------------------------------------
1. Open ONE EventSource("/v1/stream") for the app session (per tab).
2. Maintain a map: resource -> [refetch callbacks for mounted tables].
3. On `list.invalidate`, look up `data.resource` and call the refetch(es).
   Refetch hits the SAME list GET you already use — no new read endpoints.
4. Debounce: collapse a burst of pings for the same resource into one refetch.
5. Safety net: also refetch on window focus, so a dropped ping self-corrects.
6. On error/close: EventSource auto-reconnects; if it closed due to auth, do a
   token refresh first.

NOTE: notifications and the live dashboard already have their OWN dedicated
streams (/v1/notifications/stream, /v1/dashboard/live/stream) which push
absolute state, not pings. Keep using those for badges/counters. /v1/stream is
specifically for the data tables.

--------------------------------------------------------------------------------
ROLLOUT — which lists emit pings (grows by PR)
--------------------------------------------------------------------------------

  visitor_profiles.list, appointments.list, incidents.list,
  incidents.approaching_deadline, check-in queue, hosts.list,
  support_cases.list / support_cases.admin_list, dsr.list

TIER 2 (next — moderate churn):
  departments.list, branches.list, system_users.list,
  audit.recent / audit.admin_recent, invoices.for_tenant / invoices.admin_list,
  tenants.list (admin)

TIER 3 (NOT streamed — keep polling; cold/config, low value):
  plans.*, discounts.list, subscriptions.list, tenant_enums.list,
  tenant_form.*, privacy_notices.*, retention_policies.list,
  sub_processors.list, compliance.*, branding.*, *.settings

If a table you expect to update live is not in Tier 1/2, it is intentionally
polling-only for now — request it be promoted.

--------------------------------------------------------------------------------
GUARANTEES & LIMITS
--------------------------------------------------------------------------------
- Cross-instance: a change committed on any server process reaches your socket
  on any other (Redis pub/sub fan-out). No sticky sessions.
- Tenant isolation: you only ever receive pings for your own tenant; app admins
  additionally receive the global channel. Channels are scoped server-side from
  your auth principal — never from anything in the URL.
- Best-effort: if Redis is unavailable the stream degrades to nothing and your
  existing polling keeps the app correct. The ping layer never blocks a write.
- Timing: pings fire AFTER the write commits, so your immediate refetch reads
  fresh data (no read-after-write race).

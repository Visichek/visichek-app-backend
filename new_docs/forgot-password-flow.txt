================================================================================
FORGOT-PASSWORD FLOW — FRONTEND INTEGRATION GUIDE
================================================================================

Audience: frontend engineers building the "Forgot your password?" experience.
Status:   current as of 2026-05-20.

Why this changed
----------------
A single email address can belong to MANY accounts on this platform:

  * at most one PLATFORM admin (the `admins` collection), and
  * one TENANT login per tenant the person belongs to (`system_users`) — a
    person who is a super_admin of three tenants has three separate logins
    that just happen to share an email.

The old endpoint blindly emailed a reset link to EVERY matching account at
once, so one click produced 4–5 emails. The new flow is two steps: first we
look up all the accounts that share the email and let the USER pick which
one(s) to reset; only the picked accounts get an email.

All request/response bodies are camelCase (the API auto-converts). All
endpoints below are UNAUTHENTICATED.

================================================================================
THE THREE STEPS
================================================================================

  Step 1  POST /v1/auth/forgot-password            enter email → get accounts
  Step 2  POST /v1/auth/forgot-password/send       pick account(s) → send links
  Step 3  POST /v1/auth/reset-password             open link → set new password

The frontend therefore needs THREE screens/states:

  1. "Enter your email"            → calls step 1
  2. "Which account?" (a picker)   → calls step 2
  3. "Set a new password"          → a dedicated route the email link opens,
                                      which calls step 3

--------------------------------------------------------------------------------
STEP 1 — LOOK UP ACCOUNTS (no email is sent here)
--------------------------------------------------------------------------------

Request:

  POST /v1/auth/forgot-password
  Content-Type: application/json

  { "email": "jane@acme.com" }

Response 200:

  {
    "success": true,
    "message": "Account lookup complete.",
    "data": {
      "selectionToken": "x9aF...opaque...",     // echo this back in step 2
      "expiresIn": 900,                          // seconds the token is valid
      "accounts": [
        {
          "accountRef": "k3l...opaque...",       // pass to step 2 to choose this
          "type": "platform",                    // "platform" | "tenant"
          "label": "Platform Administrator",     // primary line to display
          "email": "jane@acme.com",
          "tenantId": null,                      // null for platform accounts
          "tenantName": null,
          "role": "admin",
          "roleLabel": "Platform Administrator"  // human-friendly role
        },
        {
          "accountRef": "p7q...opaque...",
          "type": "tenant",
          "label": "Acme Corp",                  // = tenant company name
          "email": "jane@acme.com",
          "tenantId": "665f...",
          "tenantName": "Acme Corp",
          "role": "super_admin",
          "roleLabel": "Tenant Super Admin"
        },
        {
          "accountRef": "z2m...opaque...",
          "type": "tenant",
          "label": "Globex Ltd",
          "email": "jane@acme.com",
          "tenantId": "660a...",
          "tenantName": "Globex Ltd",
          "role": "receptionist",
          "roleLabel": "Receptionist"
        }
      ]
    }
  }

How to render the picker:

  * For each item in `accounts`, show a selectable row.
      - `type === "platform"`  → label it as the platform/admin login. Suggested
        UI: an "VisiChek Platform" chip + `roleLabel`.
      - `type === "tenant"`    → show `tenantName` (or `label`) as the primary
        line and `roleLabel` as the secondary line. The tenant chip tells the
        user "this is your login for <company>".
  * `email` is the same for every row (it's what the user typed) — you don't
    need to show it per-row; show it once at the top ("Accounts for jane@acme.com").
  * Allow MULTI-SELECT. A person who genuinely wants to reset two of their
    logins can pick both and you send both `accountRef`s in step 2.
  * If `accounts` is EMPTY: show a neutral "If that email matches an account,
    you'll be able to continue" style message. Do NOT hard-error — see the
    enumeration note at the bottom. (`selectionToken` is still returned so your
    state machine can stay uniform; calling step 2 with it just sends nothing.)

Hold onto `selectionToken` in component state. It is single-use and expires
after `expiresIn` seconds (currently 900 = 15 min). If the user dawdles past
that, send them back to step 1.

--------------------------------------------------------------------------------
STEP 2 — SEND RESET LINK(S) FOR THE SELECTED ACCOUNT(S)
--------------------------------------------------------------------------------

Request:

  POST /v1/auth/forgot-password/send
  Content-Type: application/json

  {
    "selectionToken": "x9aF...opaque...",        // from step 1
    "accountRefs": ["p7q...opaque..."]           // the accountRef(s) the user picked
  }

Response 202:

  {
    "success": true,
    "message": "Reset link(s) sent for the selected account(s).",
    "data": { "sent": 1 }                        // how many emails were dispatched
  }

Notes:

  * `accountRefs` may contain one or many refs (multi-select). Refs that were
    not part of the original selection are silently ignored.
  * The selection is SINGLE-USE — once you call /send, the `selectionToken` is
    consumed. If the user wants to pick a different account afterwards, start
    again at step 1.
  * After a 202, show "Check your email" and stop. The email contains a button.

Errors (400):

  * Invalid / unknown `selectionToken`        → "This request expired, start again"
  * `selectionToken` already used             → same handling
  * `selectionToken` expired (>15 min)        → same handling

  {
    "success": false,
    "message": "This selection has expired",
    "code": "VALIDATION_FAILED"          // (HTTPException detail; treat 400 generically)
  }

--------------------------------------------------------------------------------
STEP 3 — THE RESET PAGE (opened by the email link)
--------------------------------------------------------------------------------

The email is an HTML message with a "Reset password" button. The button links
to a page YOU must build:

  {APP_BASE_URL}/reset-password?token=<single-use-token>

So the frontend MUST own a route at:

  /reset-password        (reads ?token=... from the query string)

We never show the raw token to the user as something to copy — it only ever
lives inside the link. Your reset page should:

  1. Read `token` from the query string.
  2. Render a "Set a new password" form (new password + confirm).
  3. Submit:

       POST /v1/auth/reset-password
       Content-Type: application/json

       { "token": "<from query string>", "newPassword": "NewStr0ng!" }

     Response 200:

       { "success": true, "message": "Password reset successfully",
         "data": { "reset": true } }

  4. On success, send the user to the login screen.

Password policy is enforced server-side (min 8 chars, upper/lower/digit/
special, not breached, no 4+ sequential/repeated, not one of the last 5
passwords). Surface the 422 `message` verbatim if validation fails.

The reset token expires 60 minutes after step 2 and is single-use. Consuming
it also revokes every active session for that account (forcing re-login
everywhere) and invalidates any other outstanding reset links for the account.

Errors (step 3):

  400  invalid / used / expired / malformed token   → "This link is no longer
                                                        valid, request a new one"
  403  the env primary platform admin cannot be reset via this flow
  404  account not found
  422  password fails policy / history check         → show `message`

================================================================================
END-TO-END SEQUENCE (happy path, single tenant account)
================================================================================

  User clicks "Forgot password"
        │
        ▼
  [Screen 1] enter email ──POST /v1/auth/forgot-password──► { selectionToken, accounts[] }
        │
        ▼
  [Screen 2] pick account(s) from accounts[]
        │   POST /v1/auth/forgot-password/send { selectionToken, accountRefs }
        ▼
  202 { sent: N }  →  "Check your email"
        │
        ▼  (user opens email, clicks the button)
  Browser opens  {APP_BASE_URL}/reset-password?token=...
        │
        ▼
  [Screen 3] set new password ──POST /v1/auth/reset-password { token, newPassword }──► 200
        │
        ▼
  Redirect to login.

================================================================================
EDGE CASES & NOTES
================================================================================

* Multiple tenants, same email: every tenant the person belongs to shows up as
  its own row in step 1, distinguished by `tenantName` + `roleLabel`. This is
  the whole point of the picker — they choose which login to recover.

* Platform + tenant on the same email: both appear; `type` tells them apart.

* Env primary admin: the .env-pinned primary platform admin is intentionally
  EXCLUDED from this flow (it never appears in `accounts`). Its recovery path is
  OTP_DEV_CODE + the env credentials, by design.

* APP_BASE_URL must be configured on the server for the email button to point
  at your reset page. If it is unset the email has no working link — this is an
  operator misconfiguration, not a frontend concern, but worth flagging in QA.

* Account enumeration trade-off: step 1 reveals whether an email has accounts
  (and how many / which tenants). This is a deliberate product decision to make
  the multi-account picker usable. If you want to soften it in the UI, you can
  always render the same "we've started the process" copy regardless of the
  count — but the API does return the real list. Security still holds where it
  matters: step 2 can only email accounts discovered in step 1, always to the
  address stored server-side, and the actual password change still requires
  possession of the emailed single-use token.

================================================================================
ENDPOINT QUICK REFERENCE
================================================================================

  POST /v1/auth/forgot-password
    body:  { email }
    200:   { selectionToken, expiresIn, accounts: [ { accountRef, type, label,
             email, tenantId, tenantName, role, roleLabel } ] }

  POST /v1/auth/forgot-password/send
    body:  { selectionToken, accountRefs: [ ... ] }
    202:   { sent }
    400:   invalid / expired / used selectionToken

  POST /v1/auth/reset-password
    body:  { token, newPassword }
    200:   { reset: true }
    400:   invalid / used / expired token
    403:   primary admin cannot be reset here
    404:   account not found
    422:   password policy / history failure
